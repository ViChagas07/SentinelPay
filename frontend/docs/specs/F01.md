# F01: Fundação do front-end

- Fase: F01
- Data: 2026-11-15
- Depende de: F00 (contrato em `frontend/docs/API_CONTRACT.md`)

## Objetivo

Criar a base técnica e visual do front-end do SentinelPay em `frontend/`, sem telas de negócio. Ao final, o projeto deve compilar, testar e construir com `npm run check`, com tema claro/escuro, três idiomas e um cliente de API tipado e testado.

## Escopo

1. Next.js App Router com TypeScript strict, Tailwind e shadcn/ui customizado.
2. ESLint, Prettier, Vitest, Playwright e script `npm run check`.
3. Fontes Instrument Serif, Geist Sans e Geist Mono via `next/font`.
4. Tokens de design em CSS variables, com `data-theme` e padrão do sistema.
5. Cliente de API com `NEXT_PUBLIC_API_URL`, `credentials: include`, tratamento de 401/403, problem+json e Zod.
6. Schemas Zod para as respostas conhecidas e hooks TanStack Query por área existente.
7. i18n leve com dicionários pt, es e en, chaves tipadas, fallback para pt, Intl e cookie.
8. Módulo único de apresentação de risco, sem recálculo de classe.
9. Páginas globais: not-found, error, loading e serviço indisponível.
10. `.env.example` e documentação de comandos.

## Fora de escopo

- Telas de login, painel, análises, boletos, contracheques, recibos, vencimentos, notificações, organização, busca e inteligência.
- Autenticação completa, refresh automático de sessão e proteção de rotas.
- Dados mockados ou fixtures visíveis ao usuário.
- Alterações no backend, infraestrutura ou knowledge base.

## Critérios de aceite

- `npm run check` executa lint, typecheck, testes e build, todos verdes.
- O tema alterna entre claro, escuro e sistema, grava a escolha em cookie e aplica `data-theme` no elemento raiz.
- O idioma alterna entre pt, es e en, grava a escolha em cookie e atualiza os textos sem recarregar a página.
- O dicionário tipado impede chave inexistente em tempo de compilação.
- O cliente de API valida toda resposta com Zod, padroniza erros e trata 401 e 403.
- Testes do cliente simulam respostas HTTP dentro do teste, sem mock na interface.
- A função de risco recebe apenas a banda da API e devolve cor, rótulo e ícone.
- Nenhuma tela calcula classe de risco a partir de score.
- As páginas globais usam a voz serif e os tokens definidos.
- Nenhum arquivo fora de `frontend/` é alterado.

## Plano de testes

- Vitest para cliente de API, schemas, i18n, tema, risco e um hook de exemplo.
- Playwright para alternância de tema e idioma, com persistência em cookie.
- `npm run check` como gate final.

## Decisões

- O access token fica em memória no módulo de auth do cliente. O refresh cookie é HttpOnly e pertence ao backend.
- O cliente de API não redireciona sozinho para login nesta fase. Ele expõe interceptores `onUnauthorized` e `onForbidden` para a F02 registrar o comportamento.
- `NEXT_PUBLIC_API_URL` é a origem da API, sem `/api/v1`. O cliente acrescenta `/api/v1`.
- As cores de risco só aparecem no contexto de risco e sempre com rótulo textual e ícone.
- O tema é resolvido por cookie no servidor para evitar flash. Sem cookie, o CSS segue `prefers-color-scheme`.

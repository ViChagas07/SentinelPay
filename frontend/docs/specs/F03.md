# F03: Autenticação e sessão

- Fase: F03
- Data: 2026-11-15
- Depende de: F01 (cliente de API e i18n) e F02 (componentes visuais)

## Objetivo

Implementar login Google OIDC pelo backend, sessão com token fora do alcance do JavaScript, proteção de rotas, logout e tratamento de expiração. Nenhuma tela de negócio.

## Restrições do backend

- `GET /api/v1/auth/google/login` responde 302 para o Google e seta `oidc_state` no host da API.
- O callback do backend responde 303 para `FRONTEND_URL` fixo, sem `return_to`.
- O callback seta `refresh_token` (HttpOnly, `Path=/api/v1/auth`) e `csrf_token` (legível por JS, `Path=/`).
- O access token só é emitido no corpo de `POST /api/v1/auth/refresh`, que exige refresh e CSRF double-submit.
- O access token expira em 15 minutos. O refresh dura 7 dias e é rotativo.
- `POST /api/v1/auth/logout` exige CSRF e limpa os cookies.

## Decisão de arquitetura

O navegador nunca recebe o access token. Route Handlers do Next.js atuam como BFF:

1. `/api/v1/auth/login` grava um cookie temporário com o `next` e redireciona ao backend.
2. Como o backend volta para `FRONTEND_URL` fixo, o middleware detecta o cookie de retorno e encaminha para `/api/v1/auth/complete`. Esse caminho fica sob `/api/v1/auth`, então o navegador envia `refresh_token` e `csrf_token` para ele.
3. O BFF troca o refresh por access token, grava o access token em cookie HttpOnly `sp_session` e encaminha os cookies rotacionados.
4. Chamadas de produto vão para `/api/v1/*` no mesmo host e o BFF injeta o Bearer a partir do cookie. Nenhum token fica em `localStorage` ou em memória do cliente.
5. Sessão expirada: o BFF tenta o refresh uma vez e repete a chamada. Se o refresh falhar, limpa a sessão e responde 401, e o cliente volta ao login com aviso discreto.

## Escopo

1. ADR da estratégia de sessão.
2. `/login` em duas colunas, com título serif, valor do produto, botão Google, termos, privacidade, idioma e tema, estados de carregando, erro e acesso negado, e parâmetro `next`.
3. Retorno do OIDC concluindo a sessão e redirecionando para `/painel` ou `next`.
4. `middleware.ts` com rotas públicas, rotas privadas e redirecionamentos.
5. `useSession` com TanStack Query lendo o usuário real via BFF, renovação e redirecionamento em expiração.
6. Logout que invalida no backend, limpa o cache e volta ao login.
7. `/termos` e `/privacidade`.
8. Casca autenticada mínima para as rotas privadas, com estados honestos de área ainda não construída.
9. Testes unitários de middleware, cookies e sessão, e e2e de roteamento e login.

## Critérios de aceite

- `npm run check` verde.
- Nenhum token legível pelo JavaScript do navegador.
- Login, rota protegida, logout e expiração cobertos.
- Middleware e helpers de sessão com testes unitários.
- Página de login acessível, com axe sem violações nos dois temas.
- Rotas privadas redirecionam para `/login?next=` sem sessão.
- `/login` redireciona para `/painel` com sessão.
- BACKEND_GAPS atualizado com o que falta no backend.

## Resultado da implementação

- O BFF espelha `refresh_token` e `csrf_token` em cookies HttpOnly `sp_refresh` e `sp_csrf` com `Path=/`, porque o backend prende o original em `/api/v1/auth`.
- O proxy genérico `/api/v1/[...path]` repassa corpo bruto, preservando multipart. Validado com upload real de PDF: 202 com `analysis_id`.
- A sessão de teste e2e é emitida pelo próprio backend via `e2e/support/create_session.py`, executado dentro do container da API. Nenhuma resposta de API é simulada na interface.
- O login com Google não foi concluído em navegador porque o container local está com `client_id=CHANGE_ME`. O e2e confirma o redirecionamento até `accounts.google.com`.
- O aviso de depreciação do `middleware.ts` é esperado no Next 16. A convenção foi mantida conforme pedido na fase.

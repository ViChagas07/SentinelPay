# F25: correção do login Google OIDC em produção

## Contexto e evidências

- Em produção, `GET https://sentinelpay1.vercel.app/api/v1/auth/login` responde `500` com corpo vazio. O mesmo handler em build local responde `302` quando `API_INTERNAL_URL` é válida.
- Reprodução local com `API_INTERNAL_URL=sentinelpay.up.railway.app` (sem esquema) devolve exatamente `500` e o log `TypeError: Invalid URL` com `input: sentinelpay.up.railway.app/api/v1/auth/google/login`.
- `GET https://sentinelpay.up.railway.app/health` e `/ready` respondem `502 Application failed to respond` no edge do Railway, o que indica que o processo da API não está atendendo. Esse é um bloqueio separado de ambiente/deploy.
- O callback atual grava `refresh_token` e `csrf_token` no domínio da API (`sentinelpay.up.railway.app`) e redireciona para `FRONTEND_URL`. O BFF em `sentinelpay1.vercel.app` não recebe cookies de outro domínio, então o refresh fica ausente e o usuário volta ao login.

## Objetivo

Fazer o login e o cadastro com Google concluírem no front-end, mesmo com API e front em domínios diferentes, sem expor tokens ao JavaScript e sem depender de cookies de terceiros.

## Decisão

1. O backend emite, após o callback, um ticket opaco de uso único com TTL curto, guardado no Redis apenas por hash da chave. O navegador é redirecionado para `FRONTEND_URL/api/v1/auth/complete?ticket=<ticket>`.
2. O BFF troca o ticket em `POST /api/v1/auth/session-ticket`, recebe access token e cookies de refresh e CSRF por canal servidor a servidor, grava `sp_session`, `sp_refresh` e `sp_csrf` no domínio do front e redireciona para o destino validado.
3. O caminho antigo, que usa o refresh cookie direto no `/complete`, permanece como fallback para desenvolvimento local e para implantações same-site.
4. O callback captura falhas do OIDC e redireciona para `FRONTEND_URL/login?reason=auth_failed&code=<codigo>&error=<codigo>` com códigos estáveis. Nunca devolve JSON de erro na URL da API.
5. A base da API é normalizada no front: espaço, aspas e ausência de esquema são corrigidos; URL inválida vira `503 auth_not_configured`, nunca `500`.

## Critérios de aceite

- `GET /api/v1/auth/login` responde `302` para `/api/v1/auth/google/login` do backend com `API_INTERNAL_URL` sem esquema.
- URL inválida em produção responde problem+json `503` com `code=auth_not_configured`.
- Callback com sucesso redireciona para `/api/v1/auth/complete?ticket=...`, sem access token nem refresh token na URL.
- Ticket é de uso único: a segunda troca responde `400 invalid_ticket`.
- Usuário novo e usuário Google existente concluem o mesmo callback.
- `error=access_denied`, state inválido, Google indisponível e bloqueio por força bruta redirecionam para o login com código seguro e mensagem traduzida em pt, es e en.
- Nenhum cookie de sessão é gravado no domínio da API para o fluxo cross-site além do refresh rotacionado e imediatamente revogado pela troca.
- Lint, typecheck, testes, build, Ruff, mypy e import-linter verdes.

## Fora de escopo

- Alterar o layout, as rotas de produto, os modelos de dados, o pipeline de IA ou o contrato de análises.
- MFA, logout global, vínculo de senha em conta Google e mudanças de escopo OAuth.
